Esta página registra o que está incompleto ou foi adiado. O objetivo é distinguir "isso foi deixado para depois" de um defeito desconhecido.

Os itens estão em quatro grupos:

- **Limitação atual**: comportamento do código de hoje que restringe o uso ou surpreende.
- **Ponto de atenção**: consequência inferida da leitura do código, sem teste ou evidência que a confirme.
- **Consideração futura**: algo que o código ou o repositório indicam como possível evolução, sem decisão tomada.
- **Funcionalidade planejada**: algo descrito no roadmap do repositório `lumora`, ainda sem implementação.

## Limitações atuais

### Funcionalidades incompletas entre tela e API

| --- | --- |
| Exclusão de galeria | A API implementa, com limpeza assíncrona das fotos. Não há controle na tela. |

### Fotos

| Item | Situação |
| --- | --- |
| URL de derivado para fotos sem derivado | `ListGalleryPhotos`, a listagem do fotógrafo, monta as URLs de miniatura e preview para toda foto, em qualquer estado. Para fotos sem derivado, a URL pode apontar para um objeto inexistente. O Studio só tenta exibir miniaturas em `AVAILABLE` ou `ARCHIVED`. A lista do cliente só devolve fotos `AVAILABLE`. |
| Reprocessar não troca o arquivo | O reprocessamento reaproveita o original fixado. Uma foto `FAILED` por arquivo inválido falha de novo. Selecionar o mesmo arquivo devolve `upload: null`, por causa do fingerprint. |
| Derivados não se atualizam sozinhos | Mudar a marca d'água ou os parâmetros dos derivados só afeta fotos novas ou reprocessadas. |
| Fotos em `PENDING_UPLOAD` abandonadas | Não há expiração nem limpeza. Elas continuam contando no resumo e em `registeredPhotoCount`. |
| Mensagens na DLQ | Sem recuperação automática. O redrive depende da correção da causa e da existência da versão do original. A expiração da mensagem não altera o estado da foto. |
| Derivados órfãos | Tentativas interrompidas e a pasta anterior de uma foto reprocessada deixam arquivos em `attempts/{attemptId}/`. Não há limpeza. |
| Só JPEG | RAW, TIFF, PNG e HEIC são recusados. |
| Nome do arquivo não exibido | A grade usa "Foto N". O schema reduzido do frontend descarta o campo `name` da resposta. |
| Estado `ARCHIVED` | Existe no enum e nos contratos. Nenhum código leva uma foto a ele. |

### Eventos e galerias

| `expiresAt` sem efeito | O valor é armazenado e editável. Nenhum código o usa. O acesso do cliente segue o prazo do link, não este campo. |

| Registros de token sem expiração física | O TTL da tabela só limpa as marcas de notificação de pagamento (`WEBHOOK#`). O registro `PUBLIC_TOKEN#` de um link vencido permanece até a substituição do link ou a exclusão do evento. |
| Edição sem controle de versão | Edições simultâneas de evento ou galeria seguem "a última escrita vence". |
| Capas | `coverUrl` é aceito pelos schemas do frontend, mas a API não o devolve. |
| Perfil sem edição | Não há rota para alterar nome ou e-mail. |

## Pontos de atenção

Os itens abaixo são consequências deduzidas da leitura do código e da configuração. Nenhum foi reproduzido, e não há teste que os confirme ou descarte. Merecem verificação antes de serem tratados como fato ou convertidos em tarefa de correção. Alguns descrevem premissas ou limites deliberados de uma decisão arquitetural, não necessariamente defeitos.

### Versão fixada e expiração de versões não correntes

O processador fixa em `sourceVersionId` a primeira versão do original a reivindicar a foto. Se o mesmo ticket for usado para um segundo envio, uma das duas versões fica não corrente, e a regra de lifecycle a remove após 14 dias.

O lease permite reivindicar novamente a mesma versão, mas não impede que ela expire no S3. A retenção de 14 dias da DLQ também não garante sua existência: segundo a [documentação do SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-configure-dead-letter-queue-redrive.html), o redrive reinicia a retenção da mensagem. Redrives sucessivos podem manter a mensagem além do prazo da versão não corrente.

Se a versão fixada tiver sido removida, a leitura por `VersionId` falha. O código trata essa falha como transitória e não substitui `sourceVersionId`. Uma foto ainda em `PROCESSING` pode continuar sem conclusão mesmo após o redrive. Esse cenário foi inferido do código e da configuração; não foi reproduzido na AWS.

Há também uma questão de integridade do original guardado: se a versão fixada for a mais antiga, o objeto que permanece como `original.jpeg` pode ser outra versão, que o processador não leu. A policy do POST exige o mesmo tamanho e tipo declarado, mas não o mesmo conteúdo. O retry do `UploadManager` reutiliza o mesmo arquivo; a credencial, por si só, não garante essa igualdade. Uma futura entrega do original precisará considerar a versão que gerou os derivados.

### Confirmação de uma entrega duplicada

Quando a reivindicação é recusada, o handler confirma a mensagem. Em uma fila standard, a mesma mensagem pode ser entregue a dois workers. Se o segundo confirmar a mensagem enquanto o primeiro ainda processa, e o primeiro falhar em seguida, pode não restar mensagem para repetir o trabalho. A foto ficaria em `PROCESSING` sem gatilho de retomada.

### Premissa de relógio do lease

O vencimento do lease é comparado com o relógio de cada invocação da Lambda. O protocolo pressupõe que diferenças entre esses relógios não sejam grandes o bastante para consumir a margem entre os tempos configurados.

Não há evidência no repositório de que essa premissa esteja sendo violada. Portanto, este item não caracteriza um defeito atual do lease; é um ponto a validar se surgirem conclusões recusadas sem causa aparente ou se os tempos do processamento forem reduzidos.

### Lote de registro não atômico

`RequestPhotoUploads` registra os arquivos em sequência. Uma falha no meio do lote responde com erro depois de parte das fotos já ter sido registrada. O cliente não recebe os tickets dessas fotos nessa resposta. A repetição do pedido é idempotente e os recupera.

### Tempo de resposta do registro

Cada arquivo de um lote custa uma transação e uma assinatura, em sequência, dentro do timeout da `studio-api`. A API aceita lotes de até 50 arquivos; o frontend atual pede 8 por vez.

## Considerações futuras

Itens que o código ou os documentos do repositório apontam como evolução possível. Não são decisões tomadas.

- **Unificar os contratos.** O `README.md` prevê que o backend passe a importar `@photos/contracts` quando o empacotamento das Lambdas suportar dependências do monorepo.
- **Dividir o template.** O `README.md` sugere nested stacks quando o template passar de cerca de mil linhas.
- **Controle de versão em edições.** O `README.md` sugere um atributo `version` caso edições concorrentes passem a causar perda de dados.
- **Limpeza de derivados órfãos.** O `README.md` menciona a limpeza futura de arquivos de tentativas interrompidas.
- **Contagem mais barata.** Caso o custo da contagem derivada se torne relevante. Veja o [ADR-009](/developers/adr/009-derived-photo-counters).
- **Região.** O `README.md` registra como pendência validar a escolha de `us-east-1` sob a LGPD.
