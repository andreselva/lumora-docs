## Status

Aceita. Origem: decisões D1, D4 e D5 do `README.md` do repositório `lumora`.

## Contexto

Em uma arquitetura serverless há duas formas extremas de organizar o código: uma função por endpoint ou uma única função para tudo.

Uma função por endpoint multiplica recursos, permissões e cold starts. Uma função única mistura cargas com necessidades diferentes de memória, tempo e permissão.

## Decisão

Criar uma função por **contexto de execução**, e não por endpoint. Uma função nova só se justifica quando o gatilho, as permissões, o timeout ou a memória são diferentes.

O template define 11 funções de produção e uma função condicional para o checkout fake de desenvolvimento.

| Função | Gatilho | Por que é separada |
| --- | --- | --- |
| `studio-api` | HTTP API, JWT do Cognito | Requisições curtas do fotógrafo, com leitura e escrita de metadados e acesso de upload. |
| `public-api` | HTTP API, authorizer do cliente | Outro público e outro conjunto de permissões: sem S3, sem filas. |
| `public-access-authorizer` | Lambda authorizer | Reconhece o token do link. Só precisa de `GetItem`. |
| `public-delivery-api` e `delivery-access-authorizer` | HTTP API e Lambda authorizer | Separam o token de entrega e as permissões de assinatura dos downloads. |
| `paymentReconciler` | Agendamento | Consulta pedidos pendentes a cada duas horas, com timeout e permissões próprios. |
| `payment-webhook` | HTTP API, sem authorizer | Outra origem: o gateway de pagamento, que se autentica conforme o adapter. Valida a credencial da notificação, consulta o provedor e aplica a transição de pagamento. |
| `fake-checkout` | HTTP API, sem authorizer | Só para dev: o lado "provedor" do gateway fake. A função é condicional no SAM. |
| `postConfirmation` | Cognito | Outro gatilho. Só precisa de `PutItem`. |
| `imageProcessor` | SQS | Mais memória e tempo, binário nativo, permissão de leitura de objetos. |
| `deletePhotosGallery` | SQS | Remove objetos nos dois buckets e itens do DynamoDB, com limites próprios. |
| `eventDeletionReconciler` | Agendamento | Roda a cada 15 minutos e só reenfileira trabalho. |

Dentro da `studio-api` e da `public-api`, o roteamento é um `switch` sobre `event.routeKey`. As rotas continuam declaradas uma a uma no template SAM.

Não há framework web nem contêiner de injeção de dependência. As dependências são instanciadas no escopo do módulo.

## Consequências

**Benefícios**

- Menos recursos para manter e um único bundle por contexto.
- Permissões mínimas por contexto. A `studio-api` não lê bytes de fotos; a `public-api` não tem acesso ao S3; o `imageProcessor` não lista nem exclui itens do DynamoDB.
- Declarar as rotas no template mantém autorização e limites configuráveis por rota, mesmo com uma só função.
- Sem camadas de framework no caminho da requisição.

**Custos**

- Cada rota é declarada em dois lugares: no template e no `switch` do handler. Uma rota presente em só um deles não funciona.
- Os handlers da `studio-api` e da `public-api` crescem a cada rota, com a lista de dependências instanciadas à mão.
- Todas as rotas compartilham memória, timeout e o conjunto de permissões da função.

## Alternativas

O `README.md` registra a intenção de dividir o template em nested stacks quando ele passar de cerca de mil linhas, e de avaliar Step Functions antes de qualquer servidor caso surja um processamento que não caiba em Lambda.

Veja a lista de gatilhos e timeouts em [Infraestrutura](/developers/architecture/infrastructure#funções-lambda).
