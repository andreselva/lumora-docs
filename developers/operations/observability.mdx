O Lumora combina logs estruturados, métricas e alarmes no CloudWatch. O SNS encaminha as notificações operacionais.

## Logs

As funções gravam no CloudWatch Logs. Os log groups declarados pelo template têm retenção de 14 dias. Use o grupo da função e o identificador da requisição ou do recurso para investigar um fluxo. O template inclui consultas salvas do Logs Insights por pedido, por foto e por nível de erro.

### Access logs da HTTP API em produção

O template habilita access logs no estágio `prod`, com retenção de 14 dias. O formato JSON inclui identificador da requisição, rota parametrizada, status HTTP e dados de latência e integração. O formato exclui o caminho bruto, headers e payload. Requisições recusadas antes da Lambda podem aparecer nesse grupo mesmo quando não geram log na função.

Após implantar o Change Set, confira `AccessLogSettings` no estágio, faça uma requisição de teste e confirme a entrega do evento no CloudWatch. Veja os pré-requisitos de IAM em [Implantação](/developers/operations/deployment#pré-requisitos-de-produção).

### Campos da `studio-api`

Cada registro de uma requisição carrega:

- `requestId`, o id da requisição no API Gateway;
- `routeKey`, por exemplo `POST /events`.

A API registra apenas erros inesperados, com a mensagem "Falha ao processar requisição" e o erro. Respostas 4xx esperadas, como validação e recurso não encontrado, não geram log da aplicação. Isso vale também para o `public-api`.

Requisições recusadas pelo JWT authorizer ou pelo `PublicAccessAuthorizer` não chegam à função de rotas e não aparecem nesses logs.

### Campos do `imageProcessor`

Cada registro de uma mensagem carrega `messageId` e `senderId`.

Os registros de falha no processamento trazem ainda:

| Campo | Conteúdo |
| --- | --- |
| `photoId`, `eventId`, `galleryId` | A foto em processamento |
| `sourceVersionId` | A versão do objeto no S3 |
| `processingAttemptId` | A tentativa, ou `null` se a falha foi antes da reivindicação |
| `stage` | A etapa em que a falha ocorreu |
| `errorName`, `errorMessage`, `stack` | O erro |

Valores de `stage`: `claim`, `getPhoto`, `headOriginal`, `validate`, `getOriginal`, `thumbnail`, `putThumbnail`, `preview`, `putPreview`, `markAvailable`, `markFailed` e `message`.

### Mensagens do `imageProcessor`

| Mensagem | Nível | Significado |
| --- | --- | --- |
| `Foto rejeitada por conteúdo inválido` | warn | Falha permanente. A foto foi marcada como `FAILED`. |
| `Erro ao processar foto` | error | Falha no caso de uso. A mensagem volta para a fila. |
| `Erro ao processar mensagem SQS` | error | Falha no handler. A mensagem volta para a fila. |
| `Mensagem SQS malformada descartada sem retry` | error | O corpo não é um evento do S3 nem um job de reprocessamento válido. A mensagem é confirmada. |
| `Reprocessamento recusado` | warn | A reivindicação do reprocessamento foi recusada. O campo `reason` traz o motivo. A mensagem é confirmada sem retry. |
| `Parser da key incorreto` | warn | A chave do objeto não segue o padrão. A mensagem é descartada. |
| `Record versionId ausente` | error | O evento do S3 veio sem versão. |
| `Ignorando s3TestEvent` | info | Evento de teste enviado pelo S3 ao configurar a notificação. |

Uma falha transitória costuma gerar dois registros de erro: um no caso de uso, com `stage` específico, e outro no handler, com `stage` igual a `message`.

Uma reivindicação recusada do processamento inicial, como a de uma mensagem duplicada, **não gera log**. O caso de uso retorna em silêncio. A do reprocessamento gera o aviso `Reprocessamento recusado`.

### Consultas úteis

Exemplos para o CloudWatch Logs Insights, no log group do `imageProcessor`.

Histórico de uma foto:

```
fields @timestamp, level, message, stage, processingAttemptId, errorMessage
| filter photoId = "ID_DA_FOTO"
| sort @timestamp asc
```

Falhas por etapa:

```
fields @timestamp
| filter level = "ERROR"
| stats count() by stage, errorName
```

Fotos rejeitadas por conteúdo:

```
fields @timestamp, photoId, eventId, stage, errorMessage
| filter message = "Foto rejeitada por conteúdo inválido"
| sort @timestamp desc
```

### Logs dos processos de exclusão

A `DeletePhotosGalleryFunction` registra `Erro ao processar mensagem de exclusão` quando uma mensagem falha. O `EventDeletionReconcilerFunction` registra `Reconciliação de exclusões de evento concluída`, com o resultado da rodada, e `Limpeza de evento parada; galerias reenfileiradas` quando reenfileira galerias. Veja [Reconciliação da exclusão de eventos](/developers/flows/event-deletion-reconciliation).

### Logs do pagamento

O `payment-webhook` e a `fake-checkout` escrevem com `service` igual a `payment-webhook`. Cada requisição do webhook carrega `requestId`.

| Mensagem | Nível | Significado |
| --- | --- | --- |
| `Transição de pagamento` | info | Auditoria de cada notificação aplicada, com `orderId`, `paymentId`, `gateway`, `notificationId` e os estados antes e depois da tentativa e do pedido. |
| `Pedido em análise: pagamento não fecha com o pedido` | error | O pedido foi para `REVIEW`. O campo `reason` traz `AMOUNT_MISMATCH` ou `PAID_AFTER_CANCEL`.  |
| `Transição de pagamento recusada` | error | O gateway informou um estado que a tentativa não aceita, como "recusado" depois de "pago". A notificação é ignorada. |
| `Notificação de pagamento sem tentativa correspondente` | warn | A referência não é uma tentativa nossa aberta com este gateway. A notificação é ignorada. |
| `Notificação de pagamento com assinatura inválida` | warn | O webhook respondeu 401. Traz o nome do gateway. |
| `Falha ao processar notificação de pagamento` | error | Falha inesperada. O webhook responde 500 e o gateway reenvia. |
| `Falha no checkout fake` | error | Falha inesperada na `fake-checkout`. |

O log group do webhook alimenta um filtro para registros de nível `ERROR`. A transição para `REVIEW` também emite a métrica `OrderInReview` quando parte do webhook, da conciliação ou da verificação pelo Studio.

## Métricas

O `imageProcessor` publica métricas no formato EMF, no namespace `Lumora`, com a dimensão `service` igual a `image-processor`. O `photoId`, o `eventId` e demais identificadores ficam só nos logs, nunca em dimensões.

| Métrica | Unidade | Significado |
| --- | --- | --- |
| `PhotoProcessed` | contagem | Foto levada a `AVAILABLE`. |
| `PhotoRejected` | contagem | Foto rejeitada por conteúdo inválido. |
| `PhotoFailed` | contagem | Falha que propagou e devolveu a mensagem à fila. |
| `ProcessingDurationMs` | milissegundos | Duração do caso de uso, a cada mensagem tratada. |
| `ReprocessRefused` | contagem | Reprocessamento recusado na reivindicação. |

Os alarmes operacionais usam métricas de fila, API, funções e pagamentos.

## Alarmes

| Alarme | Sinal |
| --- | --- |
| `PhotoProcessingDlqAlarm` | Ao menos uma mensagem visível na DLQ de processamento. |
| `DeletePhotosGalleryDlqAlarm` | Ao menos uma mensagem visível na DLQ de exclusão. |
| `HttpApi5xxAlarm` | Respostas 5xx da HTTP API, inclusive falhas de integração. |
| `LambdaErrorsAlarm` | Erros de invocação das Lambdas, agregados na conta e região. |
| `PaymentWebhookErrorsAlarm` | Soma os erros de invocação do webhook e os logs dele com nível `ERROR`. |
| `OrderInReviewAlarm` | Pedidos que entraram em `REVIEW`. |

As DLQs usam janelas de um minuto. Os demais alarmes usam janelas de cinco minutos. Todos disparam ao registrar pelo menos uma ocorrência e publicam no SNS. O destinatário de `AlarmEmail` precisa confirmar a inscrição para receber mensagens.

Para investigar mensagens na fila, veja [Solução de problemas](/developers/operations/troubleshooting#mensagens-na-dlq).

## Sinais do lado do produto

O resumo de upload, `GET /events/{eventId}/upload-summary`, é também uma ferramenta de diagnóstico. Ele mostra, por evento, quantas fotos estão em cada estado:

- `PENDING_UPLOAD` que não diminui pode indicar originais ausentes, atraso na entrega dos eventos ou falhas antes de a reivindicação ser aplicada;
- `PROCESSING` que não diminui pode indicar falhas transitórias repetidas ou ausência de uma nova tentativa, inclusive por mensagens na DLQ;
- `FAILED` indica arquivos rejeitados por conteúdo.

## Dados sensíveis nos logs

- A API não registra corpos de requisição nem tokens.
- As respostas de validação não devolvem o valor enviado, apenas o campo e o código.
- O `postConfirmation` registra `userName` e `userPoolId` a cada confirmação.
- O token do link do cliente chega no header `x-access-token`. Nenhuma função o registra.
- O webhook de pagamento não registra o corpo nem a assinatura da notificação, nem os dados do cliente do pagamento.
- Os logs de falha do processamento incluem identificadores de foto, evento e galeria, mas não o nome original do arquivo.
- Os registros `Parser da key incorreto` e `Record versionId ausente` incluem a chave do objeto no S3, que contém o `sub` do fotógrafo.
