## Ambientes

`infra/samconfig.toml` define `dev` e `prod` em `us-east-1`. Use contas distintas para as stacks, pois a tabela tem nome fixo na conta e região. Em ambos os ambientes, o SAM empacota as Lambdas e a layer do sharp. O frontend sai de `apps/web/dist` para um bucket privado atrás do CloudFront.

## Desenvolvimento

**Deploy dev** publica alterações em `main` que correspondem aos filtros do workflow e aceita execução manual. O workflow usa OIDC, executa o deploy SAM, lê os outputs da stack para configurar o build Vite e publica o site no S3. Depois invalida o cache do CloudFront.

Para iterar contra uma stack de desenvolvimento, use `pnpm dev:cloud`. O gateway fake, quando habilitado, precisa do segredo de webhook no SSM. O script `scripts/create-fake-payment-secret.sh` provisiona esse parâmetro usando o perfil e região do AWS CLI.

## Produção

1. O **CI** valida a `main`. Após uma execução bem-sucedida, **Plan production** prepara um Change Set e publica um resumo com o commit e as alterações propostas.
2. Revise o resumo e o Change Set. Confira as substituições de recursos, em especial DynamoDB, S3, Cognito, IAM e CloudFront.
3. Para aprovar, abra **Actions → Deploy production → Run workflow** na `main`. Informe o Run ID do plano revisado e confirme com `DEPLOY`.
4. O workflow confere a execução do plano e o SHA da `main`, aplica o mesmo Change Set e publica o frontend daquele commit. Depois invalida o CloudFront e executa verificações HTTP básicas.

Se a `main` avançar, revise um novo plano. Um plano sem alterações de infraestrutura pode aprovar a publicação do frontend. Se a publicação do frontend falhar após o Change Set, a infraestrutura já terá avançado. Inspecione o ponto de falha antes de repetir.

## Pré-requisitos de produção

- Configure as roles de OIDC do GitHub Actions e de execução do CloudFormation. A primeira planeja, executa e publica o frontend. A segunda gerencia os recursos da stack.
- Compare as políticas em `infra/iam` com as políticas efetivamente anexadas na AWS. Alterar os JSONs no GitHub por si só não altera o IAM. A configuração de access logs exige que a role do CloudFormation tenha as permissões de logs correspondentes antes da execução do Change Set.
- Disponibilize o par de assinatura do CloudFront no SSM. `DeliverySigningKeyParameter` referencia a chave privada e `DeliverySigningPublicKeyParameter` referencia a chave pública. A API de entregas lê a chave privada em execução.
- Confirme a assinatura do e-mail de alarmes no SNS. Valide `WebhookBaseUrl` e o cadastro no provedor antes de testar cobrança real. O gateway fake fica desativado em produção.

Em produção, o template usa a origem do CloudFront do frontend para a API e para os links públicos. Em desenvolvimento, `WebOrigin` define a base dos links e a origem principal aceita pelos buckets de upload. `SecondaryWebOrigin` pode adicionar uma origem ao CORS desses buckets.

## CI e validação

O CI executa lint, formatação, typecheck, testes unitários e de integração com DynamoDB Local, build do frontend e validação SAM. Os testes Playwright ficam disponíveis localmente por `pnpm test:e2e`.

Depois de publicar, verifique a saúde da API, o frontend, a sessão e os fluxos afetados. Para mudanças no pipeline de imagens, mantenha compatibilidade entre API, workers, itens persistidos e mensagens em trânsito. Uma atualização CloudFormation pode colocar funções de versões diferentes em execução por um intervalo.

Veja [Observabilidade](/developers/operations/observability) para verificar logs e alarmes.
